# 性能优化

模组附带一组性能优化，代码在 `Code/Perf/`。每一项只去掉原版的重复计算，游戏结果和原版相同。在 909 年、约 4000 人口、2.5 万栋建筑的大地图上，x5 速度下每帧耗时从 33ms 降到 26ms，帧率提高约 20%；每帧的内存分配减半左右，垃圾回收引起的卡顿明显减少。

## 开关与出错处理

- 设置里「性能」分组只有一个总开关，默认开。关掉后所有优化立即停用，全部走原版逻辑；重新打开时，增量维护的名单先整体重建一次
- 每项优化在 `Opt` 里有一个字段，补丁先判断它
- 某一项运行时抛出异常：只关掉这一项，本次调用交给原版，日志里记一条「性能优化 xxx 出错」。直到重启游戏或热重载才会再启用

## 各项优化

| 字段 | 原版 | 优化后 | 为什么结果相同 |
|---|---|---|---|
| `edges_incremental` | 地块变化时，地图边缘图层把所在区块和周围 8 个区块整片重画 | 只重画变化的地块和它正上、正下的邻居 | 一个像素的边缘颜色只取决于该地块和上下两个邻居 |
| `favorites_cache` | 收藏物品按钮、收藏单位按钮、地图上的收藏物品图标，每次都遍历全部物品或单位 | 维护收藏名单，每 0.5 秒重建一次，玩家切换收藏时立即重建 | 名单里的每一项在使用时仍按原版条件检查 |
| `visual_throttle` | 国界每帧重画；右下角统计面板每 5 帧重数全部单位和建筑；家族物种图标每帧重算位置 | 国界每 0.1 秒，统计面板每 25 帧，家族图标位置每 0.2 秒 | 只影响画面刷新频率，不影响模拟 |
| `wild_buildings_lazy` | 任何野生建筑（每一棵树、每一株植物）生灭，下个 tick 就重扫全部建筑，重建野生王国的建筑名单 | 只在用到名单之前才重建：遗迹刷老鼠、蔓延衰退检查 | 原版只有这两处读这份名单 |
| `city_buildings_partial` | 任何一个区域变化，就重建所有城市的建筑名单 | 只重建发生变化的城市 | 补齐了原版漏掉的变化通知，见下文 |
| `enemy_search_noalloc` | 单位找敌人时，遍历列表会创建枚举器对象，是每帧内存分配的最大来源 | 按下标遍历，逻辑相同 | 遍历顺序、随机数的消耗次数和顺序都与原版一致 |
| `stats_container_pool` | 单位每次重算属性都丢掉全部属性容器，再逐个新建 | 清空时把容器放回池子，新建时从池子取（每个线程一个池子） | 容器只被所属的属性表引用 |
| `sim_zones_buildings` | 区块建筑名单每次重算都遍历全部建筑，而实际只有约 20 个区块（共 1296 个）有变动 | 按区块维护全部建筑的索引，只登记有变动区块里的建筑 | 登记顺序与原版相同，见下文 |

### 城市建筑名单

原版靠「任何变化都全量重建」，掩盖了几处没有发出的变化通知。改成只重建变化的城市后，必须自己补上这些通知：

- 区域被划给新城市时，原版只通知被划走区域的旧城市；这里也通知新城市
- `City.setKingdom` 改变城市归属时，通知这个城市
- `City.updateCityStatus` 会用不稳定的排序重排城市的区域，名单顺序会变，所以也视为变化
- 建筑状态改变、开始拆除、被摧毁时，通知它所在的城市
- 区域的脏标记设置在很短的方法里，会被编译器内联，补丁拦不到全部调用；所以每次重建前直接扫描所有区域的脏标记

### 区块建筑名单的顺序

找建筑、找敌人时，取的是名单里第一个符合条件的，所以登记顺序会影响结果。原版的顺序是建筑总名单内部哈希表的槽位顺序：删除元素不移动其他元素，扩容也不改变槽位号。这里取出有变动区块里的建筑后，按它们在哈希表里的槽位号排序，得到和原版相同的顺序。

## 验证

号称「结果相同」的每一项都带对照验证：打开 `Opt.verify` 后，同一帧里新旧算法都跑一遍，比较结果。合并进外交大修后在上述存档上验证了 40 秒，全部一致：

| 项目 | 比较内容 | 比较次数 |
|---|---|---|
| 地图边缘 | 逐像素 | 2500 万像素 |
| 城市建筑名单 | 每个城市的名单和顺序 | 2 万个城市次 |
| 区块建筑名单 | 登记的建筑和顺序 | 8 万栋次 |
| 找敌人 | 敌人列表、选中的目标 | 36 万个列表、1.8 万次选择 |
| 属性容器 | 没有容器被两处同时持有 | 12 万个容器 |
| 收藏 | 按钮状态、图标数量 | 每帧 |

原版更新后，这些优化依赖的内部结构可能变化。更新后先按下文跑一遍验证，有不一致的项先关掉再查。

## 开发与测量

模组目录里有 `bin/` 时（本地开发），`Code/Perf/Dev/` 的开发命令通道才启用，玩家那边不会触发。命令列表在 `Dev.cs` 顶部。

- `tools/game.sh start|stop|restart|status`：启动或重启游戏，等到世界就绪才返回
- `tools/dev.sh "命令" ...`：给游戏发开发命令并等结果
- `tools/ab.sh <字段名|all> [轮数] [秒数] [速度]`：读基准档，交替关、开某项优化，比较平均帧耗时和内存分配
- 基准档放在 `bin/bench/saves/tamriel_910`（不进仓库）；`load` 会先复制到 `bin/dev/run_save` 再读，不占用玩家的存档槽

验证一遍：

```bash
tools/dev.sh "load bin/bench/saves/tamriel_910" "speed x5" "opt verify on" "wait 3" "measure verify 40" "opt verify off" "pause on"
```

输出里每项一行 `@verify <项目> ... mismatches=0`。

测量时注意：

- 比较帧耗时用不带 `detail` 的 `measure`；`detail` 打开原版 `Bench` 分项计时和额外的计时补丁，本身有开销，只用来找热点
- `measure` 期间会关掉垂直同步和帧率上限，否则帧耗时会被取整到 16.7ms 的倍数；结果里的 `game_vsync`、`game_fps_cap` 是游戏自己的设置，玩家看到的帧率要按它们折算
- 结果里的 `world` 是每秒真实时间推进的世界时间。原版每帧推进固定步长，帧率掉多少，世界就慢多少
- Unity 的渲染在单独的线程上，和模拟并行。模拟减轻后，帧耗时可能被渲染卡住；暂停时测一次，就是只剩渲染时的帧耗时
- Mac 上开着 HiDPI 时，游戏按系统画布的分辨率渲染（2K 屏开 HiDPI 是 5120×2880，像素是屏幕的 4 倍）。在 6500 人的存档上，暂停时 36 帧对关掉 HiDPI 后的 77 帧。降低游戏分辨率会被系统来回缩放，像素画和文字都会糊，只能在系统里关 HiDPI
- 世界一直在变，前后两次测量不能直接比，用 `ab.sh` 交替测
- 无风扇的笔记本满载一段时间后会降频，所有部分均匀变慢；不同时间的绝对帧耗时不可比，不测量时把游戏暂停
- 原版每 300 秒（真实时间）同步自动存档一次，大地图会冻结约 1 秒；测量结果里不带 `(gc)` 的近 1 秒卡顿多半是它
- 原版 x2 到 x20 每帧只跑一次模拟（只放大步长），x40 才每帧两次
- Mac 版游戏只有 Intel 版本，在 Apple 芯片上经 Rosetta 转译运行，绝对耗时比 Windows 上大得多；各项优化的相对比例仍然成立

改原版逻辑时容易踩的坑：

- 很短的方法（如 `CityManager.setDirtyBuildings`、`TileZone.setDirty`）会被 Mono 内联进调用方，补丁只能收到一部分调用。需要可靠地知道「发生了变化」时，读它们设置的字段，或挂在更大的方法上，并用对照验证确认
- 泛型类型上的方法挂计时补丁时拿不到 `__originalMethod`，运行时会每帧抛异常；`Measure` 已跳过这类目标
- 原版建筑没有名字，读 `Building.name` 会抛异常

## 试过但没做的

- 居民名单（原版每次房屋变动都检查全体单位的住房）：判断住房失效的条件，比如单位换城市、房屋归属变化，原版不发通知，没有可靠的增量做法
- 单位走路放到多个线程：能并行的部分每帧只有约 1.5ms，原版每批只有 256 个单位，开线程的开销抵掉了收益；要拿到收益得改变同一帧内单位的执行顺序
- 模拟隔帧推进、步长翻倍（x10 及以下，合并后不超过原版最大步长 20）：世界速度不变，平均帧耗时降约 25%，但帧耗时一快一慢交替，体感不明显。步长越大，每次推进时到期的计时器越多，AI 的活跟着变多，合 3、4 帧也没有更多收益
- 只粗算屏幕外、没在打仗的单位：原版单位做完动作会等计时器，任一帧里只有约一成单位真正跑 AI，能省的不到 3ms；镜头拉远进入地图模式后，整张地图都算在视野里，按镜头分档失效
- 寻路、AI 决策：是剩下最大的开销，但都有副作用，重写需要放宽「和原版逐帧相同」的标准
